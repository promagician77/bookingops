What happens to a booking when the payment answer never comes back

Two checkout flows run the same booking rush on MongoDB 8.3 against a CardPointe-shaped test gateway that drops, delays and times out. Plus an MCP layer in front of an old reservation API, and Twilio/Telnyx webhook checks. Every number on this page comes from a script in the repo.

Bars after each number: one per seed (5 runs; each run 220 customers arriving within 1.5 s across 40 departures). "Old pattern" is a common way booking code is written, not your code; I haven't seen it.

The two flows

Old pattern

  1. Count booked seats for the departure
  2. Charge the card (auth + capture in one call)
  3. Insert the booking
  4. Error or timeout: the customer presses Pay again, which is a new charge with a new order id

Reworked

  1. One idempotency key per checkout; one worker per key (a lease)
  2. Hold seats with one conditional update: booked + held + party ≤ capacity
  3. Auth only, unique order id per try. No answer, B or 5xx: inquireByOrderid before anything is sent again
  4. Seats held → booked, then booking + attempt state in one transaction
  5. Capture after the confirmation; a background job finishes whatever a crash left

CardPointe's own guide is blunt about a timed-out auth: "your application can not determine whether or not the transaction was successful." Retrying blindly is how one customer ends up with two charges. The reworked flow asks the gateway first.

    Telnyx Ed25519, same verdict as the SDK

    Call status for call-quality data: last write wins vs ranked merge

    An order of work, not a schedule. Measure first, then change the checkout behind a flag, then the rest.

    Measure what's failing now

    Read-only: match CardPointe reports to bookings. Find order ids with two approvals, captures with no booking, timed-out auths (respcode 62), and departures where bookings exceed capacity. That gives a baseline in dollars and seats.

    Make retries safe

    Idempotency key per checkout, a unique order id per auth, inquire before any retry, auth now and capture after the booking exists. Ship behind a flag and compare failure counts.

    Hold seats, then sweep

    Atomic seat holds with expiry, a background job that finishes or unwinds stuck checkouts, and an alert when anything stays stuck. "On hold for another guest" instead of a false "sold out".

    Lock down the webhooks

    Signature checks on every Twilio and Telnyx endpoint using the public URL and the raw body, replay windows, and a ranked status merge so call-quality numbers aren't skewed.

    MCP: read tools first

    Email and review drafting only need reads. Then propose/approve for changes. Move one tool at a time from the old service, each move gated on a parity run.

    Keep it boring in GitLab

    The fault suite runs in CI on every merge request; a short runbook per service (deploy, roll back, where logs are); docs live next to the code.

    What I'd ask for first

    • Read access to the GitLab group and the deploy setup (Hetzner, Atlas, AWS)
    • CardPointe UAT credentials and recent settlement or transaction reports
    • A staging Atlas cluster, or a recent snapshot I can restore
    • The last month of "failed booking" tickets or call-center notes
    • Which webhook URLs Twilio and Telnyx call today
    • Who approves changes that touch payments

      Not measured, or not real

      • Not CardPointe: a test gateway with the same REST paths and response fields. Real UAT timing and codes were not exercised.
      • Not your code: the "old pattern" is a common one, written by me to compare against.
      • Fault rates (3% lost answers, 1% lost requests, 1% timed out, 1% 5xx, 1% crash per step) are my assumptions.
      • One MongoDB node on a 2-vCPU container. Atlas latency will differ; the counts of oversold seats and double charges don't depend on it.
      • No language model was called. The MCP tools were driven by an MCP client.
      • Twilio and Telnyx were checked against their own SDKs offline, not with live webhooks. The call-status stream is simulated.
